# M4 Memory Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `fdt` charts the connected app's heap, external memory and RSS with GC markers on the shared time axis, and lists the allocation profile with deltas over a range. It takes heap snapshots on demand and parses them off the UI thread. It computes reachability, dominators and retained sizes, and flags lifecycle objects that are dead but still reachable, each with a readable retaining path. It also diffs a "go there and back" pair. A 5-million-object snapshot is analysed within 3 s while the UI stays responsive.

**Architecture:**
- **`fdt_vm`** gains:
  - the memory RPCs and the `GC` event;
  - binary WebSocket frames, routed to a heap-snapshot chunk channel instead of being dropped.
- **`fdt_analysis::heap`** (no GPUI) gains:
  - a streaming snapshot parser and a snapshot encoder for tests;
  - reachability, Lengauer–Tarjan dominators and retained sizes;
  - a compact held index;
  - the versioned SDK field table, the leak scan and the diff;
  - object details, read lazily from the snapshot file.
- **`fdt_store`** gains memory samples, GC records, allocation profiles and heap-snapshot records (summary, findings, diff, and the held index).
- **`fdt_capture`** gains:
  - a per-connection `MemoryHub`: the 500 ms poll, allocation profiles, and snapshot transport into a file;
  - a session-level `HeapAnalyser`: analysis on a blocking thread, with progress, cancel, re-open and diff.
- **`fdt_app`** gains:
  - the Memory tool: a chart above the Classes, Leaks and Snapshot tabs;
  - ⌘⇧S, palette commands and the sidebar count;
  - the Timeline GC lane fed by GC events, and leak cross-links.

**Tech stack:**
- Rust 1.100.0, edition 2024.
- `gpui-kit` 0.10.0 (UI crates only).
- The workspace dependencies only. **No new crates.io dependencies.** `fdt_capture` gains the workspace's `dirs` and a path dependency on `fdt_analysis`, and `fdt_analysis` gains `tempfile` as a dev-dependency.
- Flutter 3.41–3.50 for `jank_lab`.

**Deferred on purpose.** Each item is owned by a later milestone or is not in the spec:
- **Level 3, confirmed leaks** (M6, needs the probe). `FlutterMemoryAllocations` is an in-process listener and sends no VM-service events (H18).
- **MCP `get_leaks` and `get_retaining_path`** (M7). Findings and paths are plain data in the store, with `path_text`, so M7 can wrap them.
- **Exporting heap snapshots** (M7). Raw snapshots hold the VM token and home paths (H20), so M7 must redact them.
- **Live-object RPCs** (`getRetainingPath`, `getInboundReferences`, `getInstances`). Everything here is computed from the snapshot, which keeps working after a disconnect.
- **Allocation tracing, per-class external memory, and `_getAllocationProfile`'s new/old split.** None is in the spec, and the split is unverified (H7).
- **Automatic caps on snapshot files.** §8.5 keeps snapshots "until removed", and the rolling caps belong to M7.
- **`getVM._currentRSS`.** It is private, and `getProcessMemoryUsage` exists on every supported release (H19).
- **Partial results while a snapshot is analysed** (§9.2). The analysis reports its stage and can be cancelled, but publishes its result once, at the end: the whole job is under 3 s at 5M objects (H14).

## Calls made in this plan (please check)

1. **Heap snapshots are taken only on request:** ⌘⇧S, the "Take heap snapshot" button, or the palette. Never on a timer.
   - **Reason.** The app pauses for the whole write: 43–166 ms on `jank_lab`, and an extrapolated 1–4 s at 5M objects (H11).
   - **The copy** warns about the pause.
   - **Progress.**
     - While chunks arrive, the progress shows the bytes received. The total isn't known until the last chunk, so this phase is indeterminate.
     - Analysis progress is determinate.
     - Both phases can be cancelled. Cancelling a receive does not shorten the app's pause; the copy says so.
   - **Streams.** `HeapSnapshot` is subscribed just before each request and cancelled after the reply. So fdt never receives snapshots that another tool asked for.
2. **Binary frames go to a chunk channel.**
   - `RpcClient` first tries every binary frame as a snapshot frame: a `u32` offset, then `streamNotify` metadata for `HeapSnapshot`. Only if that fails is it read as UTF-8 text.
   - **Why that order.** A small final payload can be valid UTF-8 by accident (Review focus 1).
   - **Unasked-for chunks.** Chunks that arrive with no snapshot in flight are dropped.
3. **Memory for the parsed graph** (direction 3; the spike peaked at 825 MB for 5M objects, H14).
   - **Chunks go straight to a file** in the heap directory, `dirs::cache_dir()/fdt/heap`, falling back to the temp directory. They are never concatenated in memory. The parser streams from the file.
   - **Targets.**
     - Peak analysis memory is **≤ 80 B per snapshot object**: ≤ 400 MB at 5M objects, against the spike's 825 MB.
     - The held index is **≤ 32 B per reachable object**.
     - The design is in Task 6. Task 9 asserts both numbers.
   - **Freeing.** Every analysis buffer is freed when the scan ends.
   - **One full index is held:** the selected snapshot, the latest by default.
     - Every snapshot keeps a small summary: class counts, findings with their paths, and the identity hashes of tracked classes.
     - Its file stays on disk, so an older snapshot can be re-opened. That re-analyses it, in ≤ 3 s at 5M objects.
     - The direction allowed up to two parsed snapshots. One is enough, because the diff needs only the baseline's summary (Task 8). Holding two would cost another 107 MB at 5M objects.
   - **Files.**
     - A file is deleted when its snapshot is removed, on a new session, or on window close.
     - At startup, the capture removes files left by fdt processes that are no longer alive.
     - On Unix, files are created with mode 0600. They never leave the machine.
   - **Idle budget (§10.2: connected, nothing selected).**
     - With no snapshot taken, M4 holds no heap data at all.
     - After a snapshot, its held index is outside "idle" and is stated: about 4.4 MB for `jank_lab` (137k reachable objects) and about 107 MB at 5M objects.
     - Task 19 reports RSS both before and after one snapshot.
4. **Memory chart data.**
   - **Polling.** `getIsolateGroupMemoryUsage` (used, capacity, external) and `getProcessMemoryUsage` (RSS = `root.size`) are polled every 500 ms (H1, H2, H4).
   - **Unchanged samples.** A sample that changes nothing is not stored, so an idle app causes almost no publishes. That means the heap values are equal, RSS moved by less than 256 KiB, and the last stored sample is less than 5 s old.
   - **GC stream.** `GC` is subscribed at connect. Events are filtered to the app's isolate group and de-duplicated per GC (H5). The duration comes from the Δ of cumulative `time`.
   - **The Timeline GC lane switches to GC events**, and falls back to timeline GC slices for a session that has none.
     - **Reasons.** GC events belong to the app's isolate group only; the timeline also shows the vm-service group's scavenges (H6). They carry the post-GC heap for the tooltip. They match the chart's markers. And they don't depend on which timeline streams another tool records.
     - **Timeline GC slices stay** for the Raw trace and for the explanation's GC rule (M3 rule 4).
5. **The allocation profile is fetched on demand only.** It pauses the app for 15–17 ms in profile mode (H7).
   - **When:**
     - when the Classes tab opens and the newest profile is over 5 s old;
     - on "Refresh";
     - once after each heap snapshot, so the "there" and "back" moments both have class counts.
   - **Never `reset`:** other clients see its stamp (H7).
   - **`gc: true` only through a labelled switch**, "Live objects only", which is off by default. It forces a full GC that every client sees.
   - **Range deltas.**
     - Every fetched profile is kept with its time. A range compares the profiles nearest its two ends.
     - Rows are keyed by class id within one isolate. Across a hot restart they are keyed by (library, name), with a note (P15).
     - A range change never triggers a fetch, because ranges usually lie in the past.
6. **Sizes and paths.**
   - **Retained size is dominator-based.** DevTools uses the shortest-retainer tree instead (H13); the spec asks for a dominator tree.
   - **Retaining paths are BFS shortest paths from the root.** Weak classes are not followed: `_WeakProperty`, `_WeakReferenceImpl`, `FinalizerEntry` (H13).
   - **Synthetic hops get readable labels:** root slices, statics, list elements, closure contexts and captured variables (H10).
7. **Unreachable objects** are about a third of a snapshot (H8, H10).
   - They are left out of every snapshot view, count, scan and diff.
   - One line states them: "{n} unreachable objects ({bytes}) were waiting for garbage collection and are left out."
   - The Classes tab includes garbage unless "Live objects only" is on, and its copy says so.
8. **Level-1 scan** (H15).
   - **What it flags:**
     - a `State` whose `_element` is null;
     - an `Element` whose `_lifecycleState._name` is `defunct`, or whose `_widget` is null;
     - a `ChangeNotifier` whose `_debugDisposed` is true, in debug mode only.
   - **Profile mode.** A notifier pointing at the empty-listener sentinel could be disposed or simply never listened to. It is **not reported**, and the copy says so.
   - **Subclasses** are recognised by field-name prefix. The snapshot has no class hierarchy (H15).
   - **The field table** is one versioned module, keyed by Flutter minor version. An unknown version tries every row.
   - **A check that can't run** on a snapshot (a class or field is missing) is reported as not checked. It never guesses.
9. **The diff.**
   - **User packages** are the root library's package, from `getIsolate(main).rootLib`, plus `file:` libraries that `is_user_library` accepts.
   - **It also lists lifecycle classes from any package** (`State`, `Element` and `ChangeNotifier` subclasses) in their own section, "Objects with a lifecycle". This goes beyond the spec's "classes from the user's own packages".
     - **Reason.** The leaked controllers in `jank_lab` are Flutter classes, and in profile mode the diff is the only way to find the disposed one (H16).
     - **Cost.** Some framework noise. It is limited to classes whose live count grew *and* that have objects new since the baseline.
   - **Matching.** Objects are matched by identity hash (H12).
   - **Which pairs compare.** Only snapshots of the same run and isolate. The default baseline is the previous snapshot of that isolate, and the user can pick another.
10. **"Held by HTTP recording"** is the retained size of reachable `_HttpProfileData` objects (`dart:_http`), plus the value of the static `_developerProfilingData`, which `package:http_profile` clients use (fact S1). It is shown in the Snapshot tab's header. Task 18 checks it against a live app.
11. **Fixtures.**
    - Unit tests build snapshots with the Rust encoder, like M3's `perfetto::encode`.
    - One real profile snapshot is committed: `fixtures/heap/jank_lab-profile-after-leaks.dartheap`, ≤ 12 MiB.
      - Task 4 re-records it, with same-length redaction of the VM token and the user name in 1-byte and UTF-16 strings.
      - A privacy test decodes every string in it.
      - The encoder must rebuild it byte for byte, which ties every encoder-based test to the real format.
12. **⌘⇧S from any page** starts a snapshot and opens Memory › Leaks, with a Back step. That is where the pause warning, the progress and the result are.
13. **`jank_lab` gains two built-ins:** `goto_leaks`, and `pump_frames`, which drives 30 frames by hand. With `pump_frames` the leak screen builds and disposes even when the display is asleep (H0), so the memory checks of the live test don't need a drawing window.
14. **Analysis runs in the capture, and its results live in the store.** Every view, and M7's MCP later, reads one result; no view recomputes it.
15. **Chart colours come from existing tokens**, always with text labels:
    - heap used `accent`, capacity `accent` at `alpha::AREA`;
    - external `lane_state`, RSS `lane_network`;
    - scavenges `text_muted`, mark-sweep and mark-compact `warning`.

    This adds no colour tokens and no contrast tests (as M3's call 12).

## Global constraints

**Carried from M1–M3 (unchanged)**

  - Use `keymap::platform("cmd-…", "ctrl-…")`; never `secondary-…`.

  - No I/O, decoding, or work proportional to session or heap size runs on the UI thread.

## Review focus

These are the inputs most likely to hurt a real user that feature tests would not exercise by default. Each one has a test in the task that owns the code.

1. **Snapshot transport going wrong.**
   - Input: another client asks for a snapshot while fdt is subscribed; the app disconnects mid-snapshot; a chunk never comes; `Success` arrives with zero chunks; a binary frame that is ordinary UTF-8 JSON; a final payload that happens to be valid UTF-8; a second ⌘⇧S while one is running.
   - Expected: no hang and no panic, one plain error, the partial file deleted, and the next snapshot works.
   - *(Tasks 2, 11)*
2. **Hostile or odd snapshot bytes.**
   - Input: a truncated file, bad magic or an unknown data tag; a ref past `objectCount`, or a class id that is 0 or past `classCount`; a field index past the object's ref count; zero objects; no identity hashes (an old VM); a 10-byte negative Smi; a 1,000,000-long linked list, or a list of 1,000,000 elements.
   - Expected: `Err` with the byte offset, never a panic; no recursion, so deep chains can't overflow the stack; malformed fields are skipped, not trusted.
   - *(Tasks 3, 6, 7)*
3. **SDK drift.**
   - Input: a Flutter version whose fields differ or were tree-shaken; `ChangeNotifier` in another library (3.50); an app with no Flutter widgets; an unknown `flutter_version`; a subclass re-declaring a private field (`AppEvents._listeners`).
   - Expected: no false positives; a check that can't run is named in the Leaks tab ("Couldn't check notifiers in this snapshot."); the first field of a shadowed name is used.
   - *(Task 7)*
4. **Volume.**
   - Input: 5M objects; 50 snapshots in one session; a node with 1,000,000 dominator children; a GC every 10 ms for 30 minutes (180,000 records); 200 allocation profiles of 6,666 classes.
   - Expected: the budgets hold; one index is held; a tree node shows 500 children and then "{n} more"; the chart stays under the quad cap; the store stays small.
   - *(Tasks 5, 9, 13, 14, 16)*
5. **Lifecycle across restarts and sessions.**
   - Input: a snapshot, a hot restart, then a diff; ⌘N while a snapshot is held or being taken; removing the held snapshot; a reconnect; cancelling during the receive and during the analysis.
   - Expected: the diff says the snapshots can't be compared; files are deleted and memory freed; stale analysis results are dropped; selections that point at removed data clear.
   - *(Tasks 8, 11, 15)*

### Setup and memory overview

- **H0. The spike ran with the display asleep, so `jank_lab` drew no frames.** A pushed route never built.
  - Driving frames by hand made build, layout, `initState` and `dispose` run: `SchedulerBinding.handleBeginFrame(Duration(microseconds: Timeline.now))`, then `handleDrawFrame()`, every 16 ms.
  - Pauses were measured as gaps in a 1 ms `Timer.periodic` ticker on the UI isolate: 2.4 ms idle baseline, up to 25 ms while pumping.
- **H1. `getMemoryUsage {isolateId}`** → `{"type":"MemoryUsage","heapUsage":11184544,"heapCapacity":12075008,"externalUsage":2624}`, in bytes.
  - `getIsolateGroupMemoryUsage {isolateGroupId}` returns the same numbers, at 0.20 ms p50.
  - `heapUsage` excludes the AOT read-only image.
  - Home screen: profile 11.2 of 12.1 MB, debug 75.9 of 84.6 MB.
- **H2. `getProcessMemoryUsage {}`** (public since protocol 3.36) → `{"type":"ProcessMemoryUsage","root":{"name":"Process …","description":"Resident set size","size":115376128,"children":[{"name":"Dart VM",…}]}}`.
  - `root.size` is RSS. The reply is about 1 KB, at 0.2 ms p50.
  - Debug RSS on the home screen was 291 MB, against 114 MB in profile.
  - `_getProcessMemoryUsage` does not exist (`-32601`).
- **H3. Not to poll:** `getIsolate` costs 2–4.5 ms and 70–182 KB; `_getHeapMap` costs 2.5 MB and 159 ms.
- **H4. Polling cost on the app is not measurable.** 4,508 rounds of four memory RPCs in 2 s cost about 0.11 ms per RPC, and the ticker gap did not grow.

### GC stream

- **H5. `streamListen {streamId:"GC"}`.** The event, abridged:
  ```json
  {"kind":"GC","gcType":"Scavenge","reason":"new space","timestamp":1795272383990,
   "isolate":{"id":"isolates/…","isolateGroupId":"isolateGroups/5956…"},"isolateGroup":{"id":"isolateGroups/5956…"},
   "new":{"type":"HeapSpace","used":3264,"capacity":1048576,"external":0,"collections":10,"time":0.010284},
   "old":{"type":"HeapSpace","used":9331424,"capacity":10027008,"external":1984,"collections":5,"time":0.00565}}
  ```
  - **Values.**
    - `gcType` is one of `Scavenge`, `Evacuate`, `StartCMark`, `MarkSweep`, `MarkCompact`.
    - `reason` is one of `new space`, `store buffer`, `promotion`, `old space`, `finalize`, `full`, `external`, `idle`, `destroyed`, `debugging`, `catch-up`.
  - **Units.**
    - `timestamp` is epoch ms, stamped **after** the GC.
    - `time` is the **cumulative** GC seconds per space, so its Δ is the GC's duration: 0.41–0.81 ms per scavenge.
    - `used`, `capacity` and `external` are bytes after the GC. The `new` values are sometimes 0.
  - **Delivery.**
    - There is **one event per non-system isolate of the group, per GC**.
    - Same shape in debug and profile. Latency is 1–3 ms.
    - An idle app had 0 GCs in 8 s; 12 MB/s of churn gave one scavenge per 463 ms.
  - **Versions.** `gcType` arrived in protocol 3.60 and `Event.isolateGroup` in 4.9; every supported release has both.
- **H6. Placing markers.**
  - The event's `timestamp`, mapped with P6's calibration (`RunClock::from_epoch_ms`), lands within 1 ms of the timeline's GC slice.
  - Timeline `cat:"GC"` slices carry `args.isolateGroupId`, and **the vm-service isolate group's scavenges appear too**.

### Allocation profile

- **H7. `getAllocationProfile {isolateId, reset?, gc?}`** → `{"type":"AllocationProfile","memoryUsage":{…},"members":[ClassHeapStats…]}`.
  - A member:
    ```json
    {"type":"ClassHeapStats","instancesCurrent":1,"bytesCurrent":64,"instancesAccumulated":1,"accumulatedSize":64,
     "class":{"type":"@Class","id":"classes/2304","name":"_LeakyScreenState",
              "library":{"type":"@Library","uri":"package:jank_lab/scenarios/leaks.dart"},"location":{…}}}
    ```
  - **In profile mode a VM class's `library` is a Null `@Instance`**, not an `@Library`.
  - **The fields.**
    - The accumulated fields equal the current ones: both come from one heap walk, so they carry nothing new.
    - `dateLastAccumulatorReset` and `dateLastServiceGC` are strings of epoch ms.
    - The contents of `location` were not looked at. Read `location.script.uri` and `location.line` if they are present.
  - **What it counts.** The counts include unreachable garbage unless `gc:true` is passed: 196,543 instances before and 127,776 after.
  - **The parameters.**
    - The VM accepts only the JSON value `true` for them.
    - `reset:true` only stamps a date, but every client sees it.
    - `gc:true` runs a `MarkSweep` with reason `debugging`, posted to every client.
  - **Cost.**
    - Profile: 3,144 members, 2.44 MB, 51 ms p50, with a **14.7–17.1 ms app pause**.
    - Debug: 6,666 members, 5.5 MB, 137 ms.
  - **Deltas** are ours to compute. Key them by `class.id`, which is stable within an isolate group and lost on hot restart (P15).

### Heap snapshots: transport, cost and identity

- **H8. Transport.**
  - Send `streamListen {streamId:"HeapSnapshot"}`, then `requestHeapSnapshot {isolateId}` → `{"type":"Success"}`.
  - The data comes as **binary** WebSocket frames, in this layout:
    - `u32 LE data_offset`, always **512**;
    - UTF-8 JSON metadata, padded with spaces up to the offset;
    - the payload.
  - The metadata is `{"jsonrpc":"2.0","method":"streamNotify","params":{"streamId":"HeapSnapshot","event":{"type":"Event","kind":"HeapSnapshot","isolate":{…},"timestamp":…,"last":false}}}`.
  - **Chunks.**
    - Payloads are about 1,048,060 B each, except a shorter final one.
    - `last:true` is set on the final frame only.
    - Concatenate the payloads in order.
  - **The `Success` reply arrives after the last chunk:** the isolate writes the whole snapshot synchronously.
  - **Without the subscription, the VM replies `Success` and sends nothing.**
  - **`fdt_vm` drops these frames today.** `rpc.rs:271-273` logs "ignoring binary frame" for any binary frame that isn't UTF-8.
  - **What a snapshot contains.**
    - It covers the whole isolate group.
    - **The VM does not GC first**: 137k of 208k objects were reachable.
- **H11. Cost.** The app pauses for the whole write, from the request until about the last chunk.

  | Snapshot | Bytes | Objects (reachable) | Pause | Parse / BFS / dominators |
  |---|---|---|---|---|
  | profile, home | 5.8 MB | 151,231 (137,066) | 47.7 ms | 5.7 / 1.7 / 14.4 ms |
  | profile, on `/leaks` | 7.5 MB | 231,705 (143,405) | 165.6 ms | 8.7 / 2.4 / 18.0 ms |
  | profile, after leaving `/leaks` | 6.8 MB | 208,194 (137,327) | 152.9 ms | 6–7 / 1.5 / 14–19 ms |
  | debug, after leaving `/leaks` | 16.3 MB | 519,530 (488,763) | 89.5 ms | 16.7 / 7.2 / 55.6 ms |

  - **Range.** Pauses were 43–166 ms in profile (n=10) and 89–95 ms in debug (n=4).
  - **Size.** Snapshots run 32–38 B per object, at 45–181 MB/s. 5M objects would be about 165 MB and a 1–4 s pause (*unverified*).
  - **Growth.** Snapshots grow by about 100 KB each on an idle app, as garbage accumulates.
- **H12. Identity hashes are stable across snapshots.**
  - The writer assigns a hash to any object that lacks one, so **taking a snapshot changes object headers**.
  - `AppEvents`, `TextEditingController` and `_LeakyScreenState` kept their hashes across snapshots, under new object ids.
  - Strings, lists, maps, numbers and code objects get hash 0. 70,778 of 151,231 objects had one.
- **H13. Sizes.**
  - Shallow size is per object, in heap bytes; the objects sum to about the header's `shallowSize`. The committed fixture's header is 256 B above its object sum (17,202,800 vs 17,202,544), a VM accounting gap. Views must use the object sums (`reachable_bytes` plus unreachable), not the header, for totals.
  - **Retained size is not in the snapshot.**
  - Iterative Lengauer–Tarjan from object 1 matched an independent Cooper–Harvey–Kennedy run on 3 real snapshots: 0 differing `idom`s.
  - DevTools treats `_WeakProperty` and `_WeakReferenceImpl` (`dart:core`) and `FinalizerEntry` (`dart:_internal`) as weak, and uses the BFS tree for its "retained size".
- **H14. 5M objects.** 24 remapped copies of a real snapshot gave 4,996,633 objects, 25.7 M refs and 165 MB.
  - Single-threaded release, n=3: read 17–21 ms, parse 137–149 ms, BFS 39–45 ms, dominators 353–401 ms, retained sizes 30 ms, scan 6–7 ms. **Total: 570–632 ms.**
  - **Peak RSS was 825 MB:** the 165 MB buffer, the struct-of-arrays and the predecessor CSR. Memory is the constraint, not CPU.

### The snapshot format (H9, H10)

All integers are LEB128. The format, the writer and the grammar are identical in Dart 3.13 and 3.14. Dart 3.11 (Flutter 3.41) also writes the VM-isolate heap's objects with size 0; expect more zero-size objects there.

```text
Snapshot := "dartheap" flags:uleb(=0) name:str shallowSize:uleb capacity:uleb externalSize:uleb
            classCount:uleb  Class[classCount]                  class ids 1..=classCount
            referenceCount:uleb objectCount:uleb Object[objectCount]   object ids 1..=objectCount
            externalCount:uleb External[externalCount]
            identityHash:uleb[objectCount]                       0 = none; absent on very old VMs
str      := len:uleb utf8[len]        names are cut at the first '@': private names are bare (_listeners)
Class    := flags:uleb(0) name:str libraryName:str libraryUri:str reserved:str fieldCount:uleb Field[fieldCount]
Field    := flags:uleb(1 = strong) index:uleb name:str reserved:str
            index = position in the instance's ref list; superclass fields first, in memory order;
            two fields can share a name (a subclass re-declaring a private name)
Object   := classId:uleb shallowSize:uleb Data refCount:uleb ref:uleb[refCount]    ref 0 = omitted (unboxed)
Data     := tag:uleb, then: 0 none | 1 null | 2 bool v:uleb | 3 int v | 4 double f64le
            | 5 latin1 len:uleb truncLen:uleb u8[truncLen] | 6 utf16 len:uleb truncLen:uleb u16le[truncLen]
            | 7 length n:uleb | 8 name str              strings are cut at 128 code units
            int: SLEB128 for class _Mint (WriteSigned); ULEB128 otherwise, and a negative Smi is a
            10-byte ULEB that wraps to its i64 value. Skipping either is the same (stop at a byte < 0x80).
External := objectId:uleb externalSize:uleb name:str (a native finalizer symbol)
```

- **Where the VM's `heap_snapshot.md` is wrong:**
  1. identity hashes are ULEB, not `uint32`;
  2. the name data tag is 8, not 7;
  3. integer data is SLEB for `_Mint`, not ULEB. `package:vm_service` reads negative Mints wrongly.
- **Fixed layout.**
  - **Classes.** Classes 1–5 are synthetic: `Root`, `Read-Only Pages`, `Root slice`, `Isolate`, `ObjectStore`. VM cid *c* is snapshot class *c*+5.
  - **The root.** Object 1 is `Root`. Its 15 refs are:
    - `[0]`: object 2, `Read-Only Pages`, with 36,977 refs in profile;
    - 13 root slices, whose name data is "class table", "api state", "group object store" and so on;
    - `[14]`: the isolate object.
  - **The `Isolate` class is the static field table.** Its field *i* is named after static *i*, so the isolate object's ref *i* is that static's value.
    - Names are bare and not unique: there were 6 statics named `instance`. Tell them apart by the class of the value.
    - An uninitialised static points at a `Sentinel` with name data `uninitialized`.
  - **Smis** are synthetic `_Smi` objects at the end: size 0, int data, no refs.
  - **Unboxed fields are written as ref 0:** `ChangeNotifier._count` and `_ElementLifecycle.index` in profile. In debug they are boxed.
  - **Partial field tables.** User and Flutter classes have a field table that matches the refs exactly. VM-internal classes have partial ones:
    - `_List`: `[0] type_arguments`, `[1] length_`, `[2..]` elements;
    - `_GrowableList` and `_Map`: `[2] data_`;
    - `Context`: `[0] parent_`, `[1..]` captured variables;
    - `_Closure`: 4 refs but 3 names, and **`[3]` is the captured `Context`**.
  - **Not recorded:** superclasses, field owners and types, weak flags (every field says strong), allocation sites.

### Leak fields (SDK-internal; H15–H17)

| Detects | Flutter 3.47.9 source | Profile snapshot | Debug snapshot |

- **H16. `jank_lab`'s leaks after leaving `/leaks`.**

    - profile: 1 unmounted `_LeakyScreenState`, plus 19 sentinel notifiers, which are ambiguous;

    - `Analysis { summary: HeapSummary, index: HeapIndex }`.
    - This task fills the counts and classes. Tasks 7 and 8 fill the rest.
  - **Order of passes** (this decides the memory peak):
    1. Parse, then BFS retainers.
    2. Scan hook (Task 7), while the forward refs still exist.
    3. DFS numbering and predecessor lists, then **drop** `refs`, `first_ref` and `kind`.
    4. Lengauer–Tarjan, then retained sizes.
    5. Renumber, then finalize.
  - **Memory.** The peak stays ≤ 80 B per object and the held index ≤ 32 B per reachable node (Task 9 measures both). Each pass frees its arrays before the next allocates.
  - **The algorithm** (not determined by the signatures). It works in DFS-preorder space. Vertex 1 is the root, and `r` vertices are reachable through non-weak edges.
    ```rust
    // dfs: iterative, explicit stack of (object, next ref offset); vertex[v] = object, parent[v] = DFS parent.
    // preds: CSR over v of the DFS numbers of reachable, non-weak predecessors; then drop forward refs.
    // semi[v] = v, label[v] = v, ancestor[v] = 0, bucket = linked list (head/next arrays).
    for w in (2..=r).rev() {
        for &v in preds(w) { let u = eval(v); semi[w] = semi[w].min(semi[u]); }
        bucket_push(semi[w], w);
        ancestor[w] = parent[w];                       // link
        while let Some(v) = bucket_pop(parent[w]) {
            let u = eval(v);
            idom[v] = if semi[u] < semi[v] { u } else { parent[w] };
        }
    }
    for w in 2..=r { if idom[w] != semi[w] { idom[w] = idom[idom[w]]; } }
    // eval(v): if ancestor[v] == 0 { v } else { compress(v) iteratively; label[v] }
    // compress: walk ancestors to the forest root, then unwind: if semi[label[a]] < semi[label[x]]
    //           { label[x] = label[a] }; ancestor[x] = ancestor[a].
    // retained: ret[v] = shallow[vertex[v]]; for w in (2..=r).rev() { ret[idom[w]] += ret[w]; }
    ```
  - **Renumbering.**
    1. Build dominator-children lists in DFS space.
    2. Sort each list by retained size, descending, with ties broken by DFS number.
    3. BFS from the root, giving node ids in visit order. That makes every node's children contiguous.
    4. Permute into `HeapIndex`, mapping `retainer` and `idom` to node ids.
